# V1 范围与边界

> 版本：v1.1（基于 2026-10-02 术语校正）
> 状态：基线（V1 启动前不再修改）
> 读者：所有 V1 参与者

---

## 一句话定位

V1 是 Lancelot 元框架的**最小可用版本**：让用户从一组预置 adapter 中选几个，跑一次真实的 agent 对话，并且能验证"换一种记忆实现，工具代码不动"。

---

## 术语定义（V1 锁定）

Lancelot 把"具体实现"按"运行时机制"分成三层，物理位置各不相同：

| 名词 | 定义 | 物理位置 | 谁维护 | 替换方式 |
|---|---|---|---|---|
| **application**（Lancelot 自身） | Lancelot 自己的实现：CLI、扫描器、生成器、求解器、领域类型、端口契约 | `src/lancelot/` | Lancelot 维护者 | 升级 Lancelot 本身 |
| **adapter**（核心模块） | **必须重新装配**才能换的模块（记忆、模型、channel、agent 编排、基础工具）。adapter 是组装生成物的字节码组成部分。 | `adapters/`（仓库根） | 各模块作者 | 改 manifest 配置 + 重跑 compose |
| **plugin**（运行时钩子） | **不需要重新装配**的实现（GitHub 集成、飞书集成等）。plugin 由生成出来的框架**自己加载**。 | `plugins/`（仓库根） | 第三方作者 | 放进 plugins/，生成物不用变 |
| **port**（端口） | adapter 和 plugin 都必须满足的契约 | （无固定文件，跨模块） | Lancelot 定义 | — |
| **manifest** | adapter / plugin 自描述的 TOML 文件 | `<dir>/MANIFEST.toml` | 作者 | — |
| **generated framework**（生成物） | Lancelot 装配后产出的、可以脱离 Lancelot 独立运行的框架代码 | `generated/<name>/` | Lancelot 产出 | 删掉重生成 |

### adapter vs plugin 的判定问题（V1 不区分，V2 引入 plugin loader 时判定）

工具类的实现（如 `echo`、`calculator`、`github_integration`）按 V1 模型**全部**算 adapter。V2 引入 plugin loader 后，部分工具可以搬到 `plugins/`，由生成出来的框架在运行时加载——这是 V2 才做的迁移工作，V1 期间不动。

判定经验法则（V2 用）：

- **改这个模块的功能会改变生成物的核心能力吗？** → adapter
- **改这个模块只是换了"框架能访问什么外部资源"，不影响 agent 的核心运行吗？** → plugin

V1 不做这个判定，所有内置实现一律放 `adapters/`。

### 关键纪律

- adapter 是 Lancelot 装配的对象，**替换 adapter 等于重新生成框架**。
- plugin 是 Lancelot 装配后由框架加载的对象，**替换 plugin 不影响生成物的字节**。
- "adapter 也是 plugin"这种说法在 V1 模型里**不存在**——这两类是运行时机制不同的两种东西。
- V1 不实现 plugin loader。`plugins/` 目录在 V1 留空（仅 `README.md` 占位），等 V2 引入运行时钩子机制再填充。

Lancelot 整体架构文档 [`../整体架构设计.md`](../整体架构设计.md) 末尾给出了一条 8 步演化路径。V1 覆盖前 4 步 + 第 5 步的部分：

| 步骤 | 内容 | V1 覆盖？ |
|---|---|---|
| 1 | 领域层最小集 + 端口层最小集 + 最简装配器 | 是 |

## V1 范围内（必做）

### 领域层

以下概念的最小字段集和不变量：

- `Task`（任务）
- `Session`（会话）
- `Message`（消息）
- `ToolCall`（工具调用）
- `Memory`（记忆条目的引用）
- `Capability`（能力描述）
- `Manifest`（清单字段）
- `Adapter`（核心模块自描述）
- `Plugin`（运行时钩子自描述，V1 仅作类型占位）

具体字段定义见 [`03-端口契约.md`](03-端口契约.md)。

### 端口层

- `ModelPort` —— 模型调用契约
- `MemoryPort` —— 记忆读写契约
- `ToolPort` —— 工具契约
- `ChannelPort` —— 输入输出契约
- `AgentLoopPort` —— agent 循环契约
- `Registry` —— 全局注册表协议（端口层特有）

每个端口的具体方法、参数、异常、不变量见 [`03-端口契约.md`](03-端口契约.md)。

### 应用层（位于 `src/lancelot/`）

四个动作必须全部实现：

- **scan**：读取 `adapters/` 和 `plugins/` 下的 manifest，填充 Registry。**不执行任何 adapter/plugin 代码**。
- **select**：根据用户指定 + 必需检测 + 冲突检测，决定最终组合。V1 不做完整的依赖求解。
- **generate**：把选中 adapter 的源文件复制到 `generated/<name>/`，生成组合代码、配置、入口。
- **launch**：运行生成出来的框架。可以省略（用户手动启动也可）。

应用层不实现任何 agent 框架的业务规则（agent 循环、上下文压缩、工具调度、记忆检索）。

### V1 内置 adapter（位于 `adapters/`）

每个 adapter 一个目录，带 manifest + `__init__.py`：

- `adapters/memory/inmemory/` —— 满足 `MemoryPort` 的内存实现（无持久化）
- `adapters/model/mock/` —— 满足 `ModelPort` 的 mock 实现（echo 输入）
- `adapters/channel/cli/` —— 满足 `ChannelPort` 的 stdin/stdout 实现
- `adapters/agent/single_loop/` —— 满足 `AgentLoopPort` 的单 agent 循环（最简）
- `adapters/tools/echo/` —— 满足 `ToolPort` 的回显工具

每个 adapter 必须带 manifest、通过对应端口的合规性测试。

### V1 plugin 状态（位于 `plugins/`）

**V1 不实现 plugin loader。`plugins/` 目录在 V1 留空**（仅含 `README.md` 说明），等 V2 引入运行时钩子机制再填充。

### 合规性测试（位于 `tests/compliance/`）

每个端口一份测试套件：

- `test_model_port_compliance.py`
- `test_memory_port_compliance.py`
- `test_tool_port_compliance.py`
- `test_channel_port_compliance.py`
- `test_agent_loop_port_compliance.py`

**所有 V1 内置 adapter 必须通过**。这是接口约束从"声明"变成"强制"的关键一步。

### 生成物（默认输出到 `generated/<name>/`）

物理上独立、可在没有 Lancelot 装配器的环境运行的 CLI 形态框架。生成物结构见 [`07-生成物结构.md`](07-生成物结构.md)。

## V1 范围外（明确不做）

| 项 | 原因 |
|---|---|
| 真正的依赖求解器 | V1 只做必需检测 + 冲突检测，不做传递闭包、不做版本约束 |
| plugin loader（运行时钩子机制） | V1 不区分 plugin 与 adapter，所有实现都按 adapter 走 |
| 远程拉取 / 签名验证 / 信任机制 | v1 假设源文件就在本地 `adapters/` |
| GUI / HTTP API / IDE 插件 | CLI 之外的入口 |
| 多 agent 编排 | 仅有单 agent 循环 |
| 长期记忆持久化 | inmemory adapter 不写盘 |
| REM 整合 / 主动遗忘 | 属于 V1 之后的记忆层增强 |
| 真实模型调用 | V1 用 mock，预留接口让 v1.1 接 OpenAI/Anthropic |
| 可视化 adapter 选择 | CLI 参数或配置文件 |
| adapter 热更新 | 生成期固定，运行期不变 |

每一条"不做"都对应一条潜在的"看起来很合理"的需求侵蚀路径。如果未来想引入其中某条，必须先修订本文档。

## V1 成功判据（验收线）

V1 视为"完成"的硬性条件。**所有 7 条必须通过**：

1. **`lancelot scan`** 能列出 V1 内置的所有 adapter（含 mock 模型、inmemory 记忆、echo 工具、CLI channel、single_loop agent）。
2. **`lancelot compose --use memory.inmemory --use tools.echo --use model.mock --use channel.cli --use agent.single_loop`** 在 `generated/<name>/` 生成一个可独立运行的 Python CLI。
3. 启动生成的 CLI 后输入一句话，能跑完一次 agent 循环并得到回复（mock 模型回 echo）。
4. 把内置记忆实现替换为另一个 mock 实现（同样满足 `MemoryPort`），生成的框架不动一行组合代码就能跑。
5. **`pytest tests/compliance`** 全部通过，证明接口约束被强制。
6. 删除 `generated/` 后再跑一次 `compose`，能完整重生成（无隐式状态丢失）。
7. 把 `generated/<name>/` 整体复制到一台没装 Lancelot 的机器上，能直接 `python -m app.main` 跑起来（证明装配器独立性）。

第 4 条是接口契约的活体验证，第 5 条是接口契约的自动化验证，第 7 条是装配器独立性不变量的活体验证。这三条对应架构文档中的三个最关键不变量。

## 技术栈

按已对齐的方案：

- **实现语言**：Python（>= 3.11）
- **Manifest 语法**：TOML（用 `tomllib` 解析，`tomli_w` 写回）
- **生成物形态**：CLI（stdin/stdout）
- **文档节奏**：文档先行（7 份技术文档定稿后再写代码）

## 与后续版本的关系

V1 是基线，不是终点。V1.1 / V1.2 等后续小版本的引入原则：

- **不破坏** V1 任何一条成功判据
- **不修改** V1 文档中已定的契约（接口、manifest、生成物结构），只能新增
- **新增** 必须单独修订 `01-V1范围与边界.md`（追加"V1.x 增量"小节，不修改本文）
- **破坏性变更** 必须开 V2，重置文档

### V2 已知的会破坏 V1 的引入

- plugin loader（V1 不区分 adapter 与 plugin，V2 必须引入——这意味着 V1 的 `adapters/tools/` 部分内容可能搬迁到 `plugins/tools/`）
- 完整依赖求解器（V1 的 resolver 是简化的）
- 真实模型供应商（OpenAI/Anthropic 等）

每条破坏性变更触发时，必须先更新本文"V1 范围外"小节，再动代码。
